# 2026-09-27

커스텀 예외 처리를 진행했다.

지금까지는 DTO에서 잡을 수 있는 `@Valid` 관련 예외를 처리했다면,
이번에는 그 바깥에서 발생하는 예외들을 어떻게 다룰지 정리했다.

`@Valid`만으로 처리할 수 없는 예외에는 다음과 같은 것들이 있다.

DB 관련 오류

- 데이터가 NULL인 경우
- 커넥션 풀 고갈
- 제약조건 위반 (`DataIntegrityViolationException`)
- 쿼리 타임아웃

이외에도 외부 API 응답 타임아웃과 같은 문제가 발생할 수 있다.

## 제약조건을 걸면 끝나는 문제인가

처음에는 데이터가 NULL인 경우 엔티티나 DB에 제약조건을 걸면 해결되는 문제라고 생각했다.

예를 들어 `stock`은 반드시 값이 존재해야 한다면 다음과 같이 작성할 수 있다.

```java
@Column(nullable = false)
private Integer stock;
```

DB에도 `NOT NULL` 제약조건을 설정해두면 NULL 값이 저장되는 것을 막을 수 있다.

그래서 처음에는

> 제약조건을 제대로 걸어두면 굳이 별도의 예외 처리가 필요하지 않은 것 아닐까?

라고 생각했다.

하지만 제약조건과 예외 처리는 역할이 다르다.

추후에 구현할 상품 등록 기능에서 코드 버그로 인해 `stock`을 세팅하지 않고 저장할 수도 있다.

```java
Product product = new Product();
product.setName("상품 A");

// stock 설정 누락

productRepository.save(product);
```

DB의 `stock` 컬럼에 `NOT NULL` 제약조건이 있다면 INSERT 시점에 DB가 저장을 거부한다.

이 경우 Spring에서는 DB 예외를 `DataIntegrityViolationException`으로 변환해서 전달할 수 있다.

즉, 제약조건은 잘못된 데이터가 DB에 저장되는 것을 막아주지만,
**그 제약조건을 위반했을 때 요청을 어떻게 종료하고 클라이언트에게 어떤 응답을 보낼지는 별도의 문제**다.

또한 처음부터 완벽하게 모든 제약조건을 정의하기도 어렵다.

기능을 개발하면서 뒤늦게 새로운 제약조건이 필요해질 수도 있다.

예를 들어 기존에는 `stock`에 NULL을 허용하고 있었다고 가정한다.

```text
product_seq | name   | stock
------------|--------|------
1           | 상품 A | 10
2           | 상품 B | NULL
```

이 상태에서 뒤늦게 `stock NOT NULL` 제약조건을 추가하려고 하면 기존 NULL 데이터 때문에 `ALTER TABLE` 자체가 실패할 수 있다.

이 경우는 API 요청 처리 중 발생한 예외가 아니다.

따라서 `@ExceptionHandler`로 해결하는 문제가 아니라,
**마이그레이션 전에 기존 데이터를 먼저 정리해야 하는 문제**다.

결국 같은 NULL 문제처럼 보여도 발생하는 시점에 따라 대응 방법이 달라진다.

```text
잘못된 데이터 저장 시도
→ DB 제약조건으로 차단
→ 애플리케이션에서 예외 처리

기존 데이터가 이미 잘못되어 있음
→ 데이터 정리 및 마이그레이션

사용자 입력 자체가 잘못됨
→ DTO Validation
```

그래서 제약조건과 예외 처리는 대체재가 아니다.

제약조건은 잘못된 데이터가 저장되는 것을 막고,
예외 처리는 그럼에도 발생한 실패를 적절한 HTTP 응답과 로그로 변환한다.

각각 담당하는 층이 다르기 때문에 둘 다 필요하다.

## Exception인가 RuntimeException인가

예상하지 못한 예외를 마지막으로 처리하기 위해 `@ExceptionHandler`에 어떤 타입을 넣을지 고민했다.

처음에는 다음과 같이 작성하려고 했다.

```java
@ExceptionHandler(RuntimeException.class)
```

동시성 테스트를 진행하면서 발생했던 500 에러가 `RuntimeException`으로 처리되는 것을 봤기 때문이다.

하지만 다시 생각해보니 이것은 근거가 될 수 없었다.

당시에는 내가 직접 `RuntimeException`을 던졌기 때문에 당연히 `RuntimeException`으로 잡혔던 것이다.

Java의 예외 계층을 다시 보면 다음과 같다.

```text
Throwable
├── Error
│   ├── OutOfMemoryError
│   └── StackOverflowError
│
└── Exception
    ├── RuntimeException
    │   └── unchecked exception
    │
    └── 그 외
        └── checked exception
```

`RuntimeException`은 `Exception`의 자식이다.

따라서

```java
@ExceptionHandler(RuntimeException.class)
```

으로 작성하면 `RuntimeException` 하위 예외는 처리할 수 있지만,
checked exception까지 전부 처리할 수 있는 마지막 fallback은 아니다.

그래서 예상하지 못한 애플리케이션 예외를 처리하기 위한 마지막 핸들러는 다음처럼 두기로 했다.

```java
@ExceptionHandler(Exception.class)
```

`Exception`은 `RuntimeException`까지 포함하기 때문에 더 넓은 범위를 처리할 수 있다.

반면 `Error`는 `Exception`의 자식이 아니기 때문에 이 핸들러에 잡히지 않는다.

이 부분도 의도한 결과다.

`OutOfMemoryError`나 `StackOverflowError` 같은 심각한 JVM 문제까지 잡아서 정상적인 HTTP 응답으로 복구할 수 있다고 가정하는 것은 좋지 않다.

따라서 `Throwable.class`까지 잡지 않고 `Exception.class`에서 끝내는 것이 적절하다고 생각했다.

## 핸들러가 겹치면 어떻게 되는가

`Exception.class` 핸들러를 추가하면서 한 가지 걱정이 생겼다.

기존에는 `CustomException`을 다음처럼 별도로 처리하고 있었다.

```java
@ExceptionHandler(CustomException.class)
```

그런데 `Exception`은 `CustomException`의 부모 타입이기 때문에

```java
@ExceptionHandler(Exception.class)
```

을 추가하면 기존 `CustomException` 핸들러가 무력화되는 것이 아닐까 생각했다.

테스트를 진행해보니 기존 테스트 11개가 모두 통과했고,
`CustomException`도 기존처럼 409 응답으로 처리되었다.

Spring은 예외가 발생하면 매칭 가능한 핸들러 중에서
**예외 타입에 가장 가까운 핸들러를 선택한다.**

예를 들어 `CustomException`이 발생하면

```text
CustomException
Exception
```

두 핸들러 모두 후보가 될 수 있다.

하지만 `CustomException`이 더 구체적인 타입이기 때문에 해당 핸들러가 선택된다.

여기서 한 가지 더 알게 되었다.

`@ExceptionHandler`는 HTTP 상태 코드가 아니라 **예외 타입을 기준으로 매칭한다.**

즉,

```text
400이면 이 핸들러
500이면 저 핸들러
```

와 같은 방식으로 설정하는 것이 아니다.

먼저 어떤 예외가 발생했는지를 기준으로 핸들러를 선택하고,
그 핸들러가 최종적으로 어떤 HTTP 상태 코드를 반환할지 결정하는 구조다.

## 스택 트레이스는 어디로 가야 하는가

예상하지 못한 서버 예외가 발생했을 때 중요한 것은
**클라이언트에게 보여줄 정보와 서버에 남길 정보를 분리하는 것**이라고 생각했다.

클라이언트는 서버 내부의 클래스명, 패키지 경로, SQL, stack trace와 같은 정보를 알 필요가 없다.

반면 서버 개발자는 장애 원인을 분석하기 위해 stack trace가 필요하다.

따라서 다음과 같이 역할을 분리했다.

```text
클라이언트
→ 단순한 에러 코드와 메시지

서버 로그
→ 실제 Exception과 stack trace
```

예를 들어 다음과 같이 작성할 수 있다.

```java
log.error("예상하지 못한 서버 오류가 발생했습니다.", e);
```

여기서 두 번째 인자로 `Throwable`을 넘기면 stack trace까지 로그에 기록할 수 있다.

반면 다음처럼 메시지만 넘기면

```java
log.error("예상하지 못한 서버 오류: {}", e.getMessage());
```

예외 메시지만 남고 stack trace는 확인할 수 없다.

장애 분석을 위해서는 예상하지 못한 서버 예외의 경우 stack trace를 남기는 편이 좋다고 생각했다.

그리고 굳이 다음처럼 문자열을 직접 만들어 넘기지 않는다.

```java
log.error("서버 오류: " + e);
```

SLF4J의 `{}` placeholder를 사용하면 로그가 실제로 출력될 때 값이 변환되기 때문에 불필요한 문자열 연산을 줄일 수 있다.

다만 예외 객체 자체를 로그에 남길 때는 다음처럼 작성하는 것이 가장 명확하다.

```java
log.error("예상하지 못한 서버 오류가 발생했습니다.", e);
```

즉, stack trace를 없애는 것이 아니라

**클라이언트 응답에서는 제거하고 서버 로그로 옮기는 것**이다.

## 메시지는 뭉뚱그려도 되지만 상태 코드는 아니다

예상하지 못한 예외에 대해서는 다음과 같이 응답하도록 했다.

```json
{
  "errors": [],
  "code": "CM002",
  "message": "서버에 문제가 발생했습니다."
}
```

예외 메시지를 그대로 클라이언트에게 내려주면 내부 구조나 구현 정보가 노출될 수 있다.

또한 클라이언트 입장에서도

```text
NullPointerException ...
SQLSyntaxErrorException ...
ConnectionTimeoutException ...
```

같은 내부 메시지를 받아도 할 수 있는 일이 거의 없다.

그래서 예상하지 못한 서버 오류의 상세 내용은 로그에 남기고,
클라이언트 응답은 단순하게 유지하는 것이 좋다고 생각했다.

그런데 테스트를 하면서 새로운 문제가 생겼다.

예를 들어 다음 요청들도 모두 `Exception.class` 핸들러에 잡히면서 500 응답이 발생했다.

```text
존재하지 않는 URL
→ 500

깨진 JSON
→ 500
```

하지만 이 두 요청은 서버 내부 장애가 아니다.

잘못된 URL은 일반적으로 404,
잘못된 JSON은 400으로 응답해야 한다.

여기서 **에러 메시지를 숨기는 것과 HTTP 상태 코드를 정확하게 사용하는 것은 별개의 문제**라는 것을 알게 되었다.

메시지는 사람이 읽는 설명이다.

```text
서버에 문제가 발생했습니다.
```

처럼 어느 정도 추상화할 수 있다.

반면 HTTP 상태 코드는 클라이언트나 서버가 요청 결과를 판단하는 신호다.

```text
400 → 요청 자체에 문제가 있음
404 → 요청한 리소스 또는 경로를 찾을 수 없음
500 → 서버 내부 오류
```

따라서 상태 코드를 잘못 내려주면 시스템 전체에서 잘못된 판단이 발생할 수 있다.

예를 들어 실제로는 클라이언트 요청 오류인데 500으로 응답한다고 가정한다.

일부 클라이언트나 API Gateway는 5xx 응답에 대해 재시도 정책을 적용할 수 있다.

하지만 잘못된 JSON 같은 요청은 아무리 재시도해도 성공하지 않는다.

그 결과 불필요한 요청만 반복될 수 있다.

또한 모니터링에서도 문제가 생긴다.

클라이언트가 잘못된 요청을 보낸 것인데 서버는 계속 500을 기록하게 된다.

```text
실제 서버 장애 10건
클라이언트 요청 오류 990건

→ 500 에러 1,000건
```

이렇게 되면 5xx 에러율이 서버 상태를 제대로 표현하지 못한다.

운영 중 5xx 증가 알림이 발생했을 때 실제 서버 문제인지,
잘못된 요청이 많이 들어온 것인지 구분하기 어려워진다.

따라서 응답 메시지는 필요한 만큼 추상화하더라도
HTTP 상태 코드는 상황에 맞게 정확하게 내려줘야 한다.

예를 들면 다음과 같다.

```json
404
{
  "errors": [],
  "code": "CM003",
  "message": "요청한 경로를 찾을 수 없습니다."
}
```

```json
400
{
  "errors": [],
  "code": "CM001",
  "message": "입력값이 올바르지 않습니다."
}
```

```json
500
{
  "errors": [],
  "code": "CM002",
  "message": "서버에 문제가 발생했습니다."
}
```

## Exception.class가 너무 넓은 것은 아닐까

여기까지 구현하면서 한 가지 새로운 문제가 생겼다.

```java
@ExceptionHandler(Exception.class)
```

은 정말 많은 예외를 잡는다.

예상하지 못한 서버 오류를 놓치지 않는다는 장점이 있지만,
Spring이 원래 400, 404, 405 등으로 처리할 수 있었던 예외까지
전부 500으로 변환해버릴 수 있다.

즉, `Exception.class` 자체가 잘못된 것이 아니라
**너무 넓기 때문에 반드시 더 구체적인 예외 처리가 위에 존재해야 한다.**

구조를 생각하면 다음과 같다.

```text
구체적인 클라이언트 요청 오류
        ↓
400 / 404 / 405

비즈니스 예외
        ↓
CustomException

예상하지 못한 서버 예외
        ↓
Exception.class
        ↓
500
```

따라서 `Exception.class`는 모든 예외를 500으로 만드는 핸들러가 아니라,
앞에서 처리하지 못한 예외가 마지막으로 도착하는 fallback 역할을 해야 한다.
