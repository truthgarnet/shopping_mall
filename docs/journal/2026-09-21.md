# 2026-09-21

## feat인가 refactor인가?

Git 커밋 메시지를 작성하면서 `feat`와 `refactor`를 크게 구분해서 생각해본 적이 없었다.

처음에는 단순하게

* 기능을 추가하면 `feat`
* 기존 기능을 수정하면 `refactor`

라고 생각했다.

하지만 필드를 하나 추가하거나 API 응답 구조를 변경하는 경우를 생각해보니, 이것을 새로운 기능이라고 해야 할지 기존 기능의 수정이라고 해야 할지 애매했다.

그래서 `feat`, `fix`, `refactor`를 구분하는 나만의 기준을 정리해보기로 했다.

## 변경의 크기보다 변경의 목적을 기준으로 판단한다

처음에는 다음과 같은 기준을 생각했다.

> 클라이언트가 받는 결과가 변경된다면 `feat`, 내부 구현만 변경된다면 `refactor`

하지만 이 기준만으로는 `fix`를 제대로 설명할 수 없다.

예를 들어 서버가 원래 `400 Bad Request`를 반환해야 하는 상황에서 잘못해서 `500 Internal Server Error`를 반환하고 있었다고 생각해보자.

이를 수정하면 클라이언트가 받는 응답은 변경된다.

하지만 새로운 기능을 추가한 것은 아니다.

원래 의도했던 동작으로 수정한 것이므로 이 경우에는 `fix`가 더 적절하다.

따라서 단순히 **외부 응답이 변경되었는지**보다 **왜 변경했는지**를 기준으로 판단하는 것이 좋다고 생각했다.

## feat

`feat`는 **기존에 존재하지 않던 기능이나 동작을 새롭게 제공하는 경우** 사용한다.

예를 들어 기존 에러 응답이 다음과 같다고 가정한다.

```
{
  "code": "OD001",
  "message": "재고가 부족한 상품이 있습니다."
}
```

여기에 어떤 상품에서 문제가 발생했는지 클라이언트가 확인할 수 있도록 `errors` 정보를 새롭게 제공한다고 해보자.

```json
{
  "code": "OD001",
  "message": "재고가 부족한 상품이 있습니다.",
  "errors": [
    {
      "field": "items[0].productSeq",
      "message": "재고가 부족한 상품이 있습니다."
    },
    {
      "field": "items[2].productSeq",
      "message": "재고가 부족한 상품이 있습니다."
    }
  ]
}
```

기존에는 클라이언트가 받을 수 없었던 상세 오류 정보를 새롭게 제공하게 되었다.

따라서 이 변경의 목적이 **새로운 에러 상세 정보를 제공하는 것**이라면 다음과 같이 작성할 수 있다.

```
feat: 에러 응답에 필드별 상세 오류 정보 추가
```

새 API 추가, 새로운 주문 기능 추가, 새로운 조회 조건 추가 등도 같은 기준으로 `feat`라고 볼 수 있다.

## fix

`fix`는 **현재 동작이 원래 의도한 동작과 다를 때 이를 바로잡는 경우** 사용한다.

예를 들어 주문 금액 계산식이 잘못되어

```
상품 가격 10,000원 × 2개
```

를 주문했는데 20,000원이 아닌 10,000원이 계산되는 버그가 있다고 가정한다.

계산 로직을 수정했다고 해서 새로운 기능이 추가된 것은 아니다.

기존 기능이 잘못 동작하던 것을 올바르게 수정한 것이므로 다음과 같이 작성할 수 있다.

```
fix: 주문 수량이 총 금액에 반영되지 않는 문제 수정
```

다음과 같은 경우도 `fix`에 해당할 수 있다.

* 특정 조건에서 NullPointerException이 발생하는 문제 수정
* 잘못된 HTTP Status가 반환되는 문제 수정
* 재고가 중복으로 차감되는 문제 수정
* 잘못된 계산 결과 수정
* 특정 요청에서 데이터가 누락되는 문제 수정

즉,

> **원래 이렇게 동작해야 했는데 그렇게 동작하지 않았다.**

라는 설명이 가능하다면 `fix`에 가깝다.

## refactor

`refactor`는 **기능이나 외부 동작을 변경하지 않으면서 내부 코드 구조를 개선하는 경우** 사용한다.

예를 들어 기존 코드가 다음과 같다고 하자.

```java
@Autowired
private OrderService orderService;
```

이를 생성자 주입 방식으로 변경했다고 가정한다.

```java
@RequiredArgsConstructor
public class OrderController {

    private final OrderService orderService;
}
```

클라이언트 입장에서는 API의 요청과 응답이 달라지지 않는다.

하지만 코드 구조와 의존성 주입 방식은 개선되었다.

따라서 다음과 같이 작성할 수 있다.

```
refactor: OrderController 의존성 주입 방식을 생성자 주입으로 변경
```

메서드 분리, 중복 코드 제거, 클래스 구조 변경 등도 외부 동작을 그대로 유지한다면 `refactor`라고 볼 수 있다.

## 내가 정한 기준

앞으로는 변경된 코드의 양이나 파일 개수보다 **변경의 목적**을 먼저 확인하기로 했다.

```
기존에 없던 기능이나 동작을 추가했는가?
→ feat

원래 의도와 다르게 동작하던 문제를 바로잡았는가?
→ fix

기능과 동작은 그대로인데 내부 구조만 개선했는가?
→ refactor
```

예를 들어 DTO에 필드 하나를 추가했다고 해서 무조건 `feat`인 것은 아니다.

왜 그 필드를 추가했는지를 확인해야 한다.

```
새로운 정보를 API 사용자에게 제공하기 위해 필드 추가
→ feat

누락되어 있던 값을 원래 API 명세대로 반환하기 위해 필드 추가
→ fix

내부 객체 구조를 정리하기 위해 필드를 이동하거나 구조 변경
→ refactor
```

결국 커밋 타입을 판단할 때 중요한 질문은

> **“코드를 어떻게 변경했는가?”가 아니라 “왜 변경했는가?”**

라고 정리할 수 있다.

## feat인가 refactor인가?

사실 나는 git 메시지 flag를 작성할때 `feat`인가 `refactor`인가를 중요하게 생각해본 적이 없다.

기능을 추가한다면 `feat` 이고 기능을 수정한다면 `refactor` 라고 단순하게 생각했다. 하지만, 필드가 추가되는 것 같은 경우에는 기능이 추가된다고 생각해야할까 아니면 수정되었다고 생각해야할 지 고민이 들었고, 관점에 따라 다르게 생각할 수도 있다고 들었다.
그래서 `feat`과 `refactor`에 대한 정확한 기준점을 정해야하겠다는 생각이 들었다.

feat과 refactor의 기준을 클라이언트가 받는 입장에서 보면 어떨까 생각되었다.
내부적으로 고쳐지는 것은 refactor인 것이고, 클라이언트 응답하는 것이 바뀌면 feat인 것이다.

예를 들어

```
{
  "code": "OD001",
  "message": "재고가 부족한 상품이 있습니다."
}
```

같은 에러가 아래처럼 바뀔 경우는 refactror이 아닌 feat가 되는것이다.

```
{
  "code": "OD001",
  "message": "재고가 부족한 상품이 있습니다.",
  "errors": [
    { "field": "items[0].productSeq", "message": "재고가 부족한 상품이 있습니다." },
    { "field": "items[2].productSeq", "message": "재고가 부족한 상품이 있습니다." }
  ]
}
```

그렇다면 fix는 어떤 경우일까? 이 경우는 계산 로직이 잘못되어서 계산이 잘못 나올때의 경우나 버그가 발생해서 수정하는 경우에 결정하기로 했다.
