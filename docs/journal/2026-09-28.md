# 2026-09-28

어제 `Exception.class` 핸들러를 추가하면서 새로운 문제를 발견했다.

존재하지 않는 API 주소를 호출하면 `NoResourceFoundException`이 발생하는데,
이것도 `Exception.class` 핸들러에 잡혀서 500으로 응답되고 있었다.

하지만 URL을 잘못 입력한 것은 프론트의 문제이므로 4xx로 응답해야 한다.

그래서 오늘은 **상태 코드를 어떻게 되돌릴 수 있는지** 조사했다.

## Exception에서 상태 코드를 꺼낼 수 있을까

처음 떠올린 생각은 이것이었다.

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handlerServerException(Exception e) {
    // e.getXxx() 같은 걸로 상태 코드를 꺼낼 수 있지 않을까?
}
```

이미 `Exception e`로 예외 객체를 받고 있으니, 거기서 상태 코드를 꺼내면
핸들러 하나로 전부 처리할 수 있지 않을까 생각했다.

그런데 `java.lang.Exception`이 가진 메서드를 확인해보면 다음뿐이다.

```text
getMessage()
getLocalizedMessage()
getCause()
getStackTrace()
getSuppressed()
```

HTTP 상태 코드는 없다.

생각해보면 당연했다.

`java.lang.Exception`은 자바 초기부터 있는 클래스이고,
배치 프로그램이나 데스크탑 애플리케이션에서도 사용한다.

웹은 자바의 수많은 용도 중 하나일 뿐이므로, `Exception`이 HTTP를 알아야 할 이유가 없다.

## 그런데 CustomException에는 getHttpStatus()가 있다

여기서 한 가지 깨달았다.

내가 만든 `CustomException`에는 `getHttpStatus()`가 있다.

```java
public class CustomException extends RuntimeException {
    private final String code;
    private final HttpStatus httpStatus;
    private final List<FieldErrorResponse> errors;
}
```

이게 `RuntimeException`에서 물려받은 것이 아니다.

**내가 직접 필드로 넣었기 때문에 존재하는 것이다.**

즉 예외가 상태 코드를 아는 것은 기본 동작이 아니라, 누군가 넣어줬을 때만 가능하다.

`Exception`은 상태 코드를 "가져오지" 않는다. 누가 "넣어줘야" 한다.

## 상태 코드가 있을 수 있는 위치

정리해보면 상태 코드가 살 수 있는 곳은 세 군데다.

```text
① 예외 객체 안의 필드
   → 게터로 꺼낸다
   → 예) CustomException, ResponseStatusException

② 예외 클래스 위의 어노테이션
   → 리플렉션으로 읽는다
   → 예) @ResponseStatus(HttpStatus.NOT_FOUND)

③ 예외 바깥의 매핑 테이블
   → 예외는 자기가 몇 번인지 모른다
   → 예) DefaultHandlerExceptionResolver
```

②가 흥미로웠다.

`@ResponseStatus`를 붙이면 상태 코드가 **객체가 아니라 클래스 메타데이터**에 저장된다.

```java
@ResponseStatus(HttpStatus.NOT_FOUND)
public class ProductNotFoundException extends RuntimeException {
}
```

이 경우 상태 코드 정보는 분명히 존재하지만 `e.getXxx()`로는 꺼낼 수 없다.

게터가 아니라 리플렉션으로 어노테이션을 읽어야 도달할 수 있는 위치다.

③은 더 극단적이다.

예외 객체는 자기가 몇 번으로 응답되어야 하는지 **전혀 모른다.**

판단은 완전히 밖에서 한다.

생각해보면 이쪽이 자연스러운 경우도 있다.
같은 `IOException`이라도 상황에 따라 404일 수도 있고 500일 수도 있으니,
`IOException` 스스로가 정할 문제가 아니다.

## 그래서 Exception e로 받아서 꺼낼 수 있는가

①번 부류라면 가능하다.

Spring 6부터 `getStatusCode()`를 제공하는 인터페이스가 있고,
Spring MVC 표준 예외 상당수가 그것을 구현한다.

`NoResourceFoundException`도 여기에 포함된다.

**즉 그 예외 객체는 자기가 404라는 것을 이미 알고 있었다.**

내 핸들러가 `Exception e`로 받고 있어서 그 사실을 보지 못했던 것이다.

업캐스팅 때문에 정보가 가려진 상태였다.

의사코드로는 이런 모양이 된다.

```text
e가 상태 코드를 들고 있는 타입이면
    그 상태 코드를 그대로 사용한다
아니면
    500
```

Java 17이므로 `instanceof` 패턴 매칭으로 캐스팅 없이 작성할 수 있다.

주의할 점이 두 가지 있다.

첫째, 그 인터페이스의 이름이 `ErrorResponse`다.

```text
org.springframework.web.ErrorResponse       ← Spring 인터페이스
com.truthgarnet.shopping.common.ErrorResponse  ← 내가 만든 DTO
```

이름이 완전히 같으므로 한 파일에서 둘 다 쓰려면 한쪽은 풀 패키지명을 써야 한다.

둘째, 반환 타입이 `HttpStatus`가 아니라 `HttpStatusCode`다.

`HttpStatus`는 `HttpStatusCode`를 구현한 enum이다.
내 `ErrorCode`는 `HttpStatus`를 쓰고 있으므로 변환 지점이 생긴다.

## ResponseEntityExceptionHandler는 무엇을 해주는가

직접 `instanceof`로 분기하는 대신 Spring이 제공하는
`ResponseEntityExceptionHandler`를 상속하는 방법도 있다.

그런데 이걸 상속하면 무엇이 좋아지는지가 잘 이해되지 않아서 따로 알아봤다.

결론은 이 클래스가 제공하는 것이 로직이 아니라 **"판단표"**라는 것이다.

"어떤 예외가 몇 번이어야 하는가"를 예외별로 정리해놓은 목록이고,
각 예외마다 오버라이드할 수 있는 protected 훅이 딸려 있다.

목록은 대략 다음과 같다.

> 아직 소스를 직접 열어 확인하지 못했다. 검증 전 내용이다.

```text
HttpRequestMethodNotSupportedException   → 405
HttpMediaTypeNotSupportedException       → 415
HttpMediaTypeNotAcceptableException      → 406
MissingServletRequestParameterException  → 400
HttpMessageNotReadableException          → 400
NoResourceFoundException                 → 404
MaxUploadSizeExceededException           → 413
AsyncRequestTimeoutException             → 503
MissingPathVariableException             → 500
HttpMessageNotWritableException          → 500
```

여기서 마지막 두 줄이 중요하다.

이 클래스는 **모든 예외를 4xx로 바꿔주는 기계가 아니다.**

`MissingPathVariableException`은 URL 패턴에 `{id}`를 써놓고
메서드에서 파라미터를 받지 않은 경우 발생한다.

이건 클라이언트 잘못이 아니라 **내 코드 버그**이므로 500이 맞다.

즉 이 클래스가 주는 것은 4xx 변환이 아니라
**클라이언트 잘못인지 서버 잘못인지 이미 분류해놓은 표**다.

## 어려운 것은 코드가 아니라 알아내는 것

`@ExceptionHandler`를 직접 추가하는 것 자체는 어렵지 않다.

```java
@ExceptionHandler(NoResourceFoundException.class)
```

이렇게 몇 줄이면 된다.

어려운 것은 다음 세 가지다.

첫째, **그 예외가 존재한다는 것을 아는 것이다.**

나는 `NoResourceFoundException`을 어떻게 알았나.
운영에서 500이 찍혀서 알았다.

`HttpMediaTypeNotAcceptableException`은 누군가 `Accept: application/xml`을
보내는 날 알게 될 것이다.

둘째, 405 / 406 / 415 중 무엇이 맞는지 판단하는 것이다. 헷갈린다.

셋째, **Spring이 새 예외를 추가할 때 따라가는 것이다.**

이게 가장 큰 값이라고 생각했다.

`NoResourceFoundException`은 비교적 최근에 생긴 예외다.

만약 예전에 `NoHandlerFoundException`을 직접 하드코딩해뒀다면,
Spring 버전을 올리는 순간 새로 생긴 예외는 내 체인에 없으므로
**조용히 500으로 돌아간다.**

그리고 그 상황에서는 **테스트도 깨지지 않는다.**

내가 작성한 테스트는 `NoHandlerFoundException`을 검증하고 있을 테니까.

## 그럼 지금 도입해야 하는가

내 학습 원칙 중에 이런 것이 있다.

```text
문제가 발생하지 않았는데 다음 기술을 먼저 도입하지 않는다.
```

그래서 스스로 물어봤다.

지금 실제로 만난 예외는 `NoResourceFoundException` **1건**이다.

관측된 문제 1건에 20개짜리 클래스를 상속하는 것이 맞는 판단일까?

### Redis 비유를 잘못 이해했던 부분

여기서 한 가지 오해가 있었다.

Redis 예시에 나오는 "DB CPU 20%"를 처음에는
**Redis를 도입하면 추가로 발생하는 비용**이라고 이해했다.

그게 아니었다.

20%는 **"DB가 아직 안 힘들다 = 해결할 문제가 아직 없다"**는 상황을 뜻한다.

여유롭다는 신호이고, 그래서 Redis가 아직 필요하지 않다는 근거가 된다.

그리고 더 중요한 것은 `extends`와 Redis가 **비용의 종류 자체가 다르다**는 점이다.

| | Redis 조기 도입 | extends 조기 도입 |
|---|---|---|
| 런타임 비용 | 네트워크 홉, 메모리 | 없음 |
| 운영 비용 | 프로세스 감시, 장애 지점 추가 | 없음 |
| 데이터 정합성 위험 | 캐시 불일치 | 없음 |
| 되돌리기 | 어렵다 (클라이언트가 의존) | 쉽다 (키워드 하나 삭제) |
| 진짜 비용의 정체 | 시스템 복잡도 | 내 이해 부담뿐 |

자바 상속은 런타임 비용이 사실상 없다. 성능 문제가 아니다.

결국 이렇게 정리됐다.

**Redis를 잘못 도입하면 시스템이 아프다.
`extends`를 잘못 도입하면 아픈 것은 나뿐이다.**

그리고 마음에 안 들면 `extends` 한 단어를 지우고 메서드 두 개를 되살리면 된다.

따라서 "조기 도입 위험"을 이유로 `extends`를 미룰 근거는 약하다고 판단했다.

다만 채택하더라도 이유가 중요하다.

```text
X  실무 표준이라서
O  예외 목록 유지보수를 Spring에 넘기려고
```

## 선택지

아직 결정하지 않았다.

```text
A. @ExceptionHandler 를 필요한 것만 직접 추가
   - 이번 작업이 쉽다
   - 기존 코드를 건드릴 필요가 없다
   - 대신 새 예외 발견을 계속 내가 해야 한다

B. ResponseEntityExceptionHandler 상속
   - 이번에 배울 것이 많다 (상속 + 오버라이드 + 바디 통일)
   - 표준 예외는 다시 건드리지 않아도 된다
   - 되돌리기가 쉽다
```

## 응답 바디는 한 형식으로 통일한다

이건 결정했다.

`ResponseEntityExceptionHandler`를 상속하면 기본 응답 바디가
`ProblemDetail`(RFC 9457) 형식으로 나간다.

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "...",
  "instance": "/api/orderss"
}
```

이렇게 되면 기존 `errors/code/message` 형식과 두 가지가 공존하게 되고,
프론트가 응답 형식을 두 개 파싱해야 한다.

판단 기준을 **"프론트가 응답 형식을 몇 개 알아야 하는가"**로 잡았다.

그래서 표준 형식을 포기하고 기존 `ErrorResponse` 형식으로 통일하기로 했다.

```json
{
  "errors": [],
  "code": "CM003",
  "message": "요청한 경로를 찾을 수 없습니다."
}
```

RFC 표준을 따르는 이점을 버리는 대신, 클라이언트가 한 형식만 알면 되는 것을 택했다.

## 다음에 할 것

- `ResponseEntityExceptionHandler` 소스를 직접 열어서 확인한다
  - 위에 적은 예외 목록이 맞는지
  - `handleException`의 파라미터 타입과 내부 분기 구조
  - 상태 코드가 500인 예외가 실제로 있는지
- A / B 결정
- 예상되는 첫 번째 벽 (예측, 미검증)

```text
IllegalStateException: Ambiguous @ExceptionHandler method mapped for
[class org.springframework.web.bind.MethodArgumentNotValidException]
```

  부모 클래스도 `MethodArgumentNotValidException`을 처리하는데
  나도 같은 예외에 핸들러를 갖고 있어서 앱이 뜨지 않을 것으로 예상한다.

  해결하려면 내 `@ExceptionHandler` 메서드를 없애고
  부모가 제공하는 protected 훅을 오버라이드해야 한다.
  기존 `getFieldErrors()` 추출 로직은 그대로 재사용할 수 있다.

- `ErrorCode`에 4xx 공통 코드 추가 (`CM003` 부터)
- `docs/reference/error-codes.md` 표 갱신
  - `CM002` 행이 지금 누락되어 있다. 어제 커밋에 같이 들어가야 했는데 빠졌다
- 검증 항목 중 하나를 잊지 말 것
  - 일부러 NPE를 발생시켜서 **500 + 서버 로그에 stack trace**가 그대로 남는지 확인
  - 어제 얻은 것을 오늘 작업이 깨뜨리지 않았는지 보는 항목이다
