# 2026-09-14

## 예외 처리



|            | `MethodArgumentNotValidException` | `IllegalArgumentException`       |
| ---------- | --------------------------------- | -------------------------------- |
| 주체       | Spring                            | 일반 Java 코드                   |
| 주로 언제? | `@Valid`검증 실패                 | 메서드에 잘못된 값이 들어왔을 때 |
| 예시       | `@NotNull`,`@Positive`실패        | `quantity <= 0`직접 검사         |
| 발생 방식  | Spring이 자동 발생                | 보통 개발자가 직접`throw`        |
| HTTP 상태  | 보통 400                          | 처리 방식에 따라 다름            |

## 에러 응답 구조

검증 실패는 "어떤 필드가 왜 틀렸는지"가 여러 개 나올 수 있고, 재고 부족은 필드와 상관없는 비즈니스 규칙 위반이다. 두 경우를 하나의 응답 모양으로 통일하기로 했다.

```json
// 검증 실패
{
  "code": "INVALID_INPUT",
  "message": "입력값이 올바르지 않습니다.",
  "errors": [
    { "field": "items[0].quantity", "message": "수량은 1개 이상이어야 합니다." }
  ]
}

// 재고 부족
{
  "code": "OUT_OF_STOCK",
  "message": "상품A 는 재고가 부족한 상품입니다.",
  "errors": []
}
```

- `ErrorResponse(errors, code, message)` : 응답 전체
- `FieldErrorResponse(field, message)` : 필드 하나의 에러

`message`가 바깥과 안쪽에 둘 다 있는데 역할이 다르다.

- 바깥 `message` : 이 에러 전체가 뭔지 한 줄 요약 (토스트용)
- 안쪽 `message` : 이 **필드**가 왜 틀렸는지 (입력창 밑 빨간 글씨용)

처음에 `ErrorResponse` / `ErrorResponses` 로 이름을 지었더니 단수/복수로만 보여서 같은 걸로 읽혔다. 역할이 드러나게 `FieldErrorResponse`로 바꿨다.

`errors`가 없을 때는 `null`이 아니라 빈 리스트로 내려준다. 프론트에서 `errors.length`를 접근하면 `null`은 터진다.

## @ExceptionHandler는 내가 호출하는 게 아니다

처음에 `code`, `message`를 핸들러 파라미터로 받으려고 했다.

```java
handlerMethodArgumentNotValidException(MethodArgumentNotValidException e, String code, String message)
```

이건 안 된다. 이 메서드는 **Spring이 호출**하는 거라서 `code`, `message`를 넘겨줄 사람이 없다. Spring은 예외 객체나 `HttpServletRequest` 같은 정해진 것만 넣어줄 수 있다.

핸들러 하나가 예외 타입 하나를 담당하니까, 그 안에서 "지금이 무슨 상황인지"는 이미 알고 있다. 그래서 `code`와 `message`는 핸들러 안에서 직접 쓰면 된다.

```
MethodArgumentNotValidException 핸들러
    code    = "INVALID_INPUT"               ← 고정
    message = "입력값이 올바르지 않습니다."    ← 고정
    errors  = e.getFieldErrors() 변환

비즈니스 예외 핸들러
    code    = 예외에서 꺼냄
    message = e.getMessage()                ← Service가 던질 때 넣은 문구
    errors  = 빈 리스트
```

## e.getMessage()를 그대로 내보내면 안 되는 이유

`MethodArgumentNotValidException`의 `e.getMessage()`는 이런 문자열이다.

```
Validation failed for argument [0] in public com.truthgarnet.shopping.order.OrderResponse com.truthgarnet.shopping.order.OrderController.insertOrders(...) with 1 error: [Field error in object 'orderRequest' on field 'items[0].quantity': rejected value [0]; ...]
```

패키지명, 클래스명, 메서드 시그니처가 그대로 클라이언트로 나간다. 이건 Spring이 개발자 로그용으로 만든 문자열이지 사용자에게 보여줄 용도가 아니다.

`MethodArgumentNotValidException`은 `@Valid` 단계에서 터져서 Controller, Service에 도달하기도 전이다. 그래서 Service가 메시지를 넣을 방법이 애초에 없고, 핸들러가 고정 문구를 쓰는 게 맞다.

반면 `IllegalArgumentException`은 내 Service에서 직접 메시지를 넣어 던진 거라 `e.getMessage()`를 그대로 써도 된다.

## 왜 CustomException을 만들었나

```
1. ErrorResponse에 code 필드를 넣기로 함

2. IllegalArgumentException은 "재고 부족"만 던지는 게 아니다
   → 라이브러리 내부, 다른 비즈니스 규칙 위반, 코드 실수 전부 이 타입으로 들어올 수 있음
   → 핸들러가 code를 "OUT_OF_STOCK"으로 확정할 수 없음      ← 핵심 문제

3. 예외 타입으로 구분: OutOfStockException
   → 되긴 하는데, 예외마다 클래스 + 핸들러가 1:1로 늘어남

4. 예외 값으로 구분: CustomException(code, message)
   → 핸들러 하나, 클래스 하나로 모든 비즈니스 예외 처리
```

한 줄로 말하면, **표준 예외는 어떤 비즈니스 에러인지 식별할 수 없어서, 클라이언트에 내려줄 에러 코드를 예외가 직접 들고 있게 했다.**

```java
@Getter
public class CustomException extends RuntimeException {

    private final String code;

    public CustomException(String code, String message) {
        super(message);      // message는 부모가 관리 → getMessage()
        this.code = code;    // code는 RuntimeException에 없으니 내가 보관
    }
}
```

- `RuntimeException` 상속 → `@Transactional` 기본 롤백 대상 (2026-09-03 롤백 정책 참고)
- `code` 는 생성 후 바뀔 일이 없으니 `final`

### trade-off

`code`가 문자열이라 `"OUT_OF_STCOK"` 같은 오타를 컴파일러가 못 잡는다. 예외가 2~3개로 늘어나 문자열이 흩어지면 `enum ErrorCode`로 묶고, HTTP 상태까지 enum이 들고 있게 바꿀 여지가 있다. 지금은 예외가 하나라 아직 안 한다.
