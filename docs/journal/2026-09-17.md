## 생성자를 만들 때 왜 final를 작성해야할까?

처음에 개발할 때, 생성자 주입을 위해서 `@Autowired`로 작성했다.

근데 아래와 같이 노란색 줄이 발생헀다.

오류는 아니지만, 경고하는 줄으로서 잘 작성했다고 생각했는데, 왜 이렇게 나오는 지 궁금해졌다.

![1789606715045](images/2026-09-17/1789606715045.png)

테스트 및 실행은 잘 진행되었다.

Spring이 빈(bean) 하나를 만들 때는 아래와 같은 과정을 거친다.

```
1. 인스턴스 생성 (생성자 호출)
2. 의존성 주입 (필드/세터 채우기)
3. 초기화 콜백
```

이 때 `@Autowired`는 2번 단계에서 주입(필드 주입)을 진행하고, `@RequiredArgsConstructor` 는 1번 단계에서 주입(생성자 주입)이 일어난다.

```java
@Autowired
private ProductRepository productRepository;
```

더 자세하게 설명하자면, Spring이 객체를 먼저 만든 다음(기본 생성자 또는 존재하는 아무 생성자로), 리플렉션 (Field.set(...))을 이용해서 필드에 직접 값을 넣는 방식이다.`RequiredArgsConstructor`

반면, `@RequriedArgsConstructor`은 컴파일 시점에 실제 생성자를 만들어준다.

```java
public OrderService(OrderRepository orderRepository, ...) {
    this.orderRepository = orderRepository;
    ...
}
```

그렇다면, **주입하지 못했을 때는 어떤 일이 발생할까?**

```
{
    "timestamp": "2026-09-17T01:10:45.373Z",
    "status": 500,
    "error": "Internal Server Error",
    "trace": "java.lang.NullPointerException: Cannot invoke ...
    "message": "Cannot invoke \"com.truthgarnet.shopping.product.ProductRepository.findByProductSeqInOrderByProductSeqAsc(java.util.List)\" because \"this.productRepository\" is null",
    "path": "/orders"
}
```

`this.productRepository\" is null",` 의 오류를 통해서 의존성 주입이 실패한 것을 알 수 있다.

그렇다면 본론으로 다시 돌아와서

`@RequreidArgsConstructor`은 왜 private final에 주입을 하게 되는 걸까?

주입하는 순서를 확인하면 알게 된다.

순수 Java에서

```java
public class Foo {
    public Foo(String name) {   // (A) 생성자 "정의"
        this.name = name;
    }
}

Foo f = new Foo("hello");   // (B) 생성자 "호출"
```

컴파일러가 Foo를 .class 파일 안에 "Foo 생성자가 있다"라고 정보를 담아둔다.`

**프로그렘이 실행** 되면서 실제로 Foo라는 객체를 메모리에 만들고, "hello"라는 진짜 값을 그 생성자 안에 담아주듯

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final ProductRepository productRepository;
    private final OrderItemRepository orderItemRepository;

    ...
}
```

`@RequiredArgsConstructor`는 **필수 필드를 파라미터로 받는 생성자를 만들어주는 Lombok 어노테이션**이다.

여기서 필수 필드에는 `final`이 붙은 필드와 Lombok의 `@NonNull`이 붙은 필드가 포함된다.

따라서 의존성 필드에 `final`을 선언하면 `@RequiredArgsConstructor`가 해당 필드를 생성자의 파라미터에 포함시킨다.

```java
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final ProductRepository productRepository;
}
```

위 코드는 컴파일 시점에 다음과 같은 생성자가 만들어진다.

```java
public OrderService(
        OrderRepository orderRepository,
        ProductRepository productRepository
) {
    this.orderRepository = orderRepository;
    this.productRepository = productRepository;
}
```

반대로 `final`이나 Lombok의 `@NonNull`이 붙은 필드가 하나도 없다면 생성자에 포함할 필수 필드가 없기 때문에 인자가 없는 생성자가 만들어진다.

## log.debug("{}", ) vs log.debug(" " + )

### 성능 차이

둘의 차이가 없을 꺼라고 생각하고 익숙한 방법으로 `log.debug(" " + )` 문자열 뒤에 추가하는 것으로 작성했었다.

그런데 확인 결과, `" " +`의 방법은 **호출되기 전에 인자가 먼저 평가되는 방식**으로 진행된다고 한다.

```java
1. missingSeqs.toString() 실행
2. StringBuilder로 문자열 이어붙이기
3. 완성된 String을 들고 debug() 호출
4. debug 레벨이 꺼져 있음 → 그냥 리턴
```

`log.debug("{}", )`의 형식은 문자열 조립을 레벨 확인 이후로 미루는 것으로 진행된다.

```java
1. 포맷 문자열 "missing: {}"(상수)과 missingSeqs 참조만 넘김
2. 내부에서 isDebugEnabled() 확인
3. 꺼져 있음 → 바로 리턴. toString()도 안 부름
```

하지만, 이 경우는 레벨 확인의 차이라서 `log.debug`에서는 차이가 있을 수 있지만, 보통 켜져 있는 `log.warn`의 경우에는 성능 차이를 기대하기 어렵다.

### toString() 예외를 던질 경우

```java
log.warn("주문 실패: " + orderEntity);
```

에서 `OrderEntity.toString`이 Lombok @ToString으로 연관 엔티티까지 타고 들어가다 LazyInitializationException이 나거나, 순한 참조로 인해 StackOverflowError가 나는 경우가 존재한다.

`{}, `의 방식은 toString()이 SLF4J 내부에서 실행되기 때문에, SLF4J가 Throwable을 잡아서 [FAILED toString()]으로 찍고 계속 진행할 수 있다.

### 고정 문자열

로그를 검색하는 곳에서도 차이가 발생한다.

+를 사용하면 아래처럼 이미 완성된 문자열이 SLF4J에 전달된다.

```
상품이 존재하지 않는 Seqs: [3]
상품이 존재하지 않는 Seqs: [7]
상품이 존재하지 않는 Seqs: [3, 7]
```

뒤의 상품 번호가 계속 달라지기 때문에 각각 다른 문자열이 된다.

반면 {}를 사용하면 SLF4J에는 메시지와 값이 분리된 형태로 전달된다.

따라서 이후에 구조화된 로그 형태로 저장한다면 같은 종류의 로그르르 구분하거나 집계하기가 쉬워진다.

예를 들어

```
seq 3  → 840건
seq 7  → 310건
seq 12 → 50건
```

이런 결과를 보면 단순히

존재하지 않는 상품 요청이 많이 발생했다가 아닌, 3번 상품 요청이 유독 많이 들어오는 가를 파악할 수 있다.

로그를 단순한 출력 문자열이 아니라 검색하고 집계의 역할을 하는 것을 세삼 깨달았다.

더 나아가면 해당 로그가 10분 동안 1,000건 이상 발생했다는 알림도 만들 수 있다.

`JSON Encoder`이나 SLF4J의 `Key-Value`을 이용하면 된다.

### Key-Value Logging

원래 작성했던 코드를

```java
log.warn("상품이 존재하지 않는 Seqs: {}", missingSeqs);
```

```java
log.atWarn()
    .addKeyValue("missingSeqs", missingSeqs)
    .log("상품이 존재하지 않습니다.");
```

처럼 작성할 수 있다.

```java
message = "상품이 존재하지 않습니다."

key   = "missingSeqs"
value = [3, 7]
```

처럼 해석이되고, 이 로그를 Encoder로 통해 출력 형식을 결정할 수 있다.

일반 Encoder를 사용 시

```
2026-09-18 05:00:00 WARN OrderService
상품이 존재하지 않습니다. missingSeqs=[3, 7]
```

JSON Encoder를 사용 시

```json
{
  "@timestamp": "2026-09-18T05:00:00",
  "level": "WARN",
  "logger": "OrderService",
  "message": "상품이 존재하지 않습니다.",
  "missingSeqs": [3, 7]
}
```

와 같이 변환할 수 있다.
