# 2026-09-09

## 🔵 락 유무에 따른 성능 테스트

1000개의 작업을 동시에 요청하여 비관적 락이 있는 경우와 없는 경우의 처리 시간을 비교했다.


| 상태              |   로그 켬 |   로그 끔 |
| ----------------- | --------: | --------: |
| 락 있음 (MariaDB) | 2190.82ms | 1548.47ms |
| 락 없음 (MariaDB) | 1756.46ms | 1253.05ms |

처음에는 락을 사용하면 요청들이 순차적으로 처리되기 때문에 락을 사용하지 않는 경우와 성능 차이가 훨씬 클 것이라고 예상했다.

하지만 실제 측정 결과는 약 300ms 정도밖에 차이가 나지 않았다.

여기서 단순히 실행 시간만 비교해서는 안 된다는 것을 알게 되었다.

## 🟢 락이 없는 테스트에서 이상한 점

락이 없는 테스트의 결과를 확인해보니 1000개의 요청이 모두 성공한 것이 아니었다.

예를 들어 특정 테스트에서는 성공한 요청이 10~12개 정도밖에 되지 않았다.

처음에는 다음과 같이 생각했다.

> "락이 없으니까 1000개의 요청이 모두 동시에 실행되고, 따라서 1000개가 성공하는 것 아닌가?"

하지만 애플리케이션의 스레드 수와 실제 DB에서 동시에 실행할 수 있는 쿼리 수는 서로 다르다.

중간에 **DB Connection Pool**이 존재하기 때문이다.

## 🟢Thread Pool과 Connection Pool은 다르다

예를 들어 테스트에서 1000개의 스레드를 생성했다고 하더라도,

```text
Thread
1000개
   ↓
HikariCP
10 connections
   ↓
MariaDB
```

HikariCP의 `maximum-pool-size`가 10이라면 DB 커넥션을 동시에 사용할 수 있는 작업은 최대 10개다.

나머지 스레드는 즉시 실패하는 것이 아니라 **커넥션이 반환되기를 기다린다.**

즉,

```text
1000 Threads
     ↓
10개 → DB 작업 진행
990개 → Connection 대기
```

앞의 작업이 끝나서 커넥션을 반환하면 대기하고 있던 다른 스레드가 해당 커넥션을 받아 작업을 이어서 수행할 수 있다.

따라서

```text
maximum-pool-size = 10
→ 성공 요청이 무조건 10개
```

라고 볼 수는 없다.

## 🔵 Connection Pool 크기 변경 실험

`application.properties`의 HikariCP 설정을 변경하면서 테스트를 진행했다.

```properties
spring.datasource.hikari.maximum-pool-size=10
```

측정 결과는 다음과 같았다.


| maximum-pool-size | 성공 |
| ----------------: | ---: |
|                 1 |    1 |
|                10 |   10 |
|                20 |   12 |
|                50 |   12 |

Connection Pool을 1 → 10으로 증가시켰을 때 성공 개수가 증가했다.

하지만 20 이상으로 증가시켜도 성공 개수가 12에서 더 이상 증가하지 않았다.

따라서 현재 결과만 보고

```text
pool-size 10 → Connection Pool 병목
pool-size 20 → Thread 병목
```

이라고 바로 결론 내리기는 어렵다.

Connection Pool 외에도 다음과 같은 원인이 있을 수 있다.

- 여러 트랜잭션이 같은 재고 값을 동시에 읽는 문제
- 재고 부족으로 인한 예외
- 트랜잭션 충돌
- Connection timeout
- 테스트 코드 내부의 다른 예외
- 실제 동시에 실행되는 Thread 개수

따라서 실패한 요청의 **예외 종류를 분류해서 확인하는 과정이 추가로 필요하다.**

## 🔵 Connection Pool이 작으면 어떤 일이 발생할까?

예를 들어 다음과 같은 환경을 생각해볼 수 있다.

```text
Thread = 100
maximum-pool-size = 1
```

DB 커넥션은 하나뿐이므로 한 순간에는 하나의 요청만 DB를 사용할 수 있다.

```text
Thread 1   → Connection 획득 → DB 작업
Thread 2   ┐
Thread 3   │
Thread 4   ├─ Connection 대기
...
Thread 100 ┘
```

즉, 락을 사용하지 않아도 Connection Pool 자체가 DB 접근을 사실상 직렬화할 수 있다.

다만 중요한 점은 나머지 99개의 요청이 **즉시 실패하는 것이 아니라 대기한다는 것**이다.

HikariCP의 `connectionTimeout` 안에 커넥션을 얻으면 정상적으로 처리되고, 그 시간 동안 커넥션을 얻지 못하면 예외가 발생한다.

기본 `connectionTimeout`은 보통 30초다.

따라서 DB 작업 하나가 매우 오래 걸리는 상황에서는 다음과 같은 현상이 발생할 수 있다.

```text
Connection 1개
      ↓
앞 요청들이 계속 점유
      ↓
대기 요청 증가
      ↓
connectionTimeout 초과
      ↓
Connection is not available 예외
```

## 🔵 반대로 Connection Pool이 크면 어떤 일이 발생할까?

그렇다면 풀 사이즈를 크게 만들면 더 빨리 작업이 이뤄질까라는 생각을 했다.

근데, 테스트를 하니 오히려 느려진 것을 알 수 있다.

예를 들어, 식당 홀에 들여보낼 수 있는게 50명이라고 할때 웨이터는 손님들을 응대하느라 막상 서빙을 못하는 상황이 발생할 수 있다. 10명이라고 하면 응대 서빙이 훨씬 효율적으로 돌아갈 수 있다. 

```
pool 10:  580 ─── 590        폭 10ms
pool 50:            667 ────────── 754    폭 87ms
```

## 🔵 동시성 테스트에서 발견한 또 다른 특징

락 없이 동일한 테스트를 반복했을 때 실패 횟수가 일정하지 않았다.

```text
expected: <999> but was: <957>
expected: <999> but was: <958>
```

매번 결과가 달라진다는 것은 여러 스레드의 실행 순서에 따라 결과가 바뀌고 있다는 의미다.

즉, 전형적인 **Race Condition**의 특징을 확인할 수 있었다.

```text
Thread A ─┐
Thread B ─┤
Thread C ─┤
Thread D ─┘

누가 먼저 조회하고
누가 먼저 수정하고
누가 먼저 Commit하는지

→ 실행할 때마다 달라질 수 있음
```

따라서 동시성 테스트에서는 단순히

```text
테스트 실행 시간
```

만 보는 것이 아니라 다음 값들을 함께 확인해야 한다.

- 성공 요청 수
- 실패 요청 수
- 최종 재고
- 발생한 예외 종류
- 전체 처리 시간
- Connection Pool 대기 시간
-

## 🟢 이번 실험에서 배운 점

처음에는

```text
Thread 1000개
= DB 요청 1000개가 동시에 실행
```

된다고 생각했다.

하지만 실제 구조는 다음과 같다.

```text
Thread Pool
    ↓
Connection Pool
    ↓
DB
```

Thread가 많다고 해서 DB 쿼리도 동일한 개수만큼 동시에 실행되는 것은 아니다.

DB에 접근하려는 작업은 Connection Pool의 크기에 의해 한 번 더 제한된다.

또한 Connection Pool 크기만 조정한다고 해서 동시성 문제가 해결되는 것도 아니다.

이번 테스트에서 중요한 점은 **성능 테스트와 정합성 테스트를 분리해서 봐야 한다는 것**이다.

락이 없는 버전이 더 빠르더라도 데이터가 잘못된다면 의미 있는 성능 향상이라고 볼 수 없다.

다음 테스트에서는 각 요청이 실패한 이유를 예외별로 집계해서,

```text
성공
재고 부족
Connection timeout
Lock timeout
기타 예외
```

형태로 나누어 확인해볼 필요가 있다.
