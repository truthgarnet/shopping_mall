# 2026-09-20

## 커스텀 에러 코드 설계

처음에는 에러 코드를 다음과 같이 작성했다.

```
PRODUCT_NOT_FOUND("PRODUCT_NOT_FOUND", HttpStatus.BAD_REQUEST)
```

작성하고 보니 enum 상수 이름과 code 값이 모두 `PRODUCT_NOT_FOUND`로 같았다. 같은 문자열을 두 번 관리할 필요가 있는지, 프론트엔드에서 에러를 구분하기에 적절한 방식인지 고민하게 됐다.

`PRODUCT_NOT_FOUND`처럼 의미가 드러나는 코드도 이해하기 쉽다는 장점이 있다. 다만 이번에는 에러가 어느 도메인에 속하는지 일관된 형식으로 구분할 수 있도록, 도메인별 접두사와 일련번호를 조합하기로 했다.

### 도메인 분류 기준

에러가 어떤 데이터를 다루는지만 보기보다는, 어떤 동작이나 상황에서 발생하는지를 기준으로 도메인을 정했다.

예를 들어 `OUT_OF_STOCK`은 재고와 관련된 에러지만, 여기서는 재고 부족으로 주문을 진행할 수 없는 상황을 나타낸다. 따라서 주문 도메인의 에러로 보고 `OD`로 분류했다.

반면 `PRODUCT_NOT_FOUND`는 주문 과정이 아니더라도 발생할 수 있다. 예를 들어 `GET /products/7`로 상품을 조회했을 때 해당 상품이 없다면 발생하는 에러다. 따라서 상품 도메인의 에러로 보고 `PD`로 분류했다.

접두사는 다음과 같이 정했다.

| 도메인 | 접두사              | 의미    |
| ------ | ------------------- | ------- |
| 주문   | `OD` | Order   |
| 상품   | `PD` | Product |
| 공통   | `CM` | Common  |

### 코드 부여 규칙

에러 코드는 도메인 접두사 뒤에 세 자리 일련번호를 붙이는 형태로 작성한다. 각 도메인 안에서 필요할 때마다 `001`, `002`처럼 순서대로 번호를 부여하기로 했다.

예를 들어 상품 도메인의 첫 번째 에러 코드는 다음과 같이 작성할 수 있다.

```
PRODUCT_NOT_FOUND("PD001", HttpStatus.BAD_REQUEST)
```

enum 상수 이름은 개발자가 에러의 의미를 이해할 수 있도록 유지하고, 외부에 전달하는 에러 코드는 정해진 형식으로 관리한다.

### 삭제된 코드는 재사용하지 않기

에러 코드가 삭제되더라도 해당 번호는 다시 사용하지 않기로 했다. 예를 들어 `PD002`를 삭제했고 마지막으로 부여한 코드가 `PD003`이라면, 다음 코드는 `PD004`가 된다.

프론트엔드에는 기존 에러 코드를 기준으로 분기하는 로직이 남아 있을 수 있다. 이때 삭제된 코드를 다른 의미로 재사용하면, 새로운 에러를 이전 에러로 인식해 의도하지 않은 처리를 할 수 있다.

따라서 한 번 사용한 코드는 다른 의미로 재사용하지 않고, 새로운 에러에는 새로운 번호를 부여한다. 코드의 형식을 통일하는 것뿐 아니라, 프론트엔드와 약속한 의미가 바뀌지 않도록 관리하는 것을 원칙으로 삼았다.
