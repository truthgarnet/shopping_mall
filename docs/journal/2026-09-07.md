### 격리 수준

동시성을 공부하다가 **격리 수준** 개념이 등장했다. 이 개념은 왜 필요할까 아래의 상황을 보면, A와 B과 동시에 발생했다고 했을 때, A도 B도 재고 10개인 상태에서 읽는다.

```
현재 재고 = 10

트랜잭션 A                       트랜잭션 B
-------------------------      -------------------------
재고 조회 → 10
                               재고 조회 → 10
재고 변경 → 9
                               재고 변경 → 9
COMMIT
                               COMMIT
```

그렇게 A도 B도 같은 상품에서 1개를 주문했지만 재고가 9인 상태로 끝나는 것을 알 수 있다.

그래서 우리는 트랜잭션을 완전히 **분리**해야한다.

하지만, 격리를 한다고 해서 무조건 좋은 일은 아니다. 마구잡이로 격리를 했다가는 동시 처리 성능이 크게 떨어질 수 있다.

보통 DB는 4가지의 격리 수준을 제공한다.


| 격리 수준          | 격리 정도 | 대략적인 의미                                                        |
| ------------------ | --------- | -------------------------------------------------------------------- |
| `READ UNCOMMITTED` | 낮음      | 커밋 안 된 데이터도 볼 수 있음                                       |
| `READ COMMITTED`   | ↑        | 커밋된 데이터만 봄                                                   |
| `REPEATABLE READ`  | ↑        | 같은 트랜잭션에서 같은 데이터를 다시 읽을 때 일관성을 더 강하게 보장 |
| `SERIALIZABLE`     | 가장 높음 | 트랜잭션들이 순차 실행된 것과 같은 수준의 결과를 목표로 함           |

관리자가 가격 변경하는 예시를 보면, 고객이 10,000원을 보고 주문을 처리하고 있었는 데 다시 상품을 조회하니 관리자가 변경을 진행헀다. 다시 상품을 보니 20,000이 되어버리는 것이다. 고객 입장에서는 황당할 것 이다.

```
주문 Transaction B             관리자 Transaction A
──────────────────────────────────────────────

BEGIN

상품 조회
→ 10,000원

                               가격 변경
                               10,000 → 20,000
                               COMMIT

상품 다시 조회
→ 20,000원  ← 어?

COMMIT
```

그렇기 때문에, 한 트랜잭션(작업)에서는 다른 트랜잭션에서 작업이 진행되더라도 데이터를 유지할 수 있게 할 수 있다.

이것을 `REPEATABLE READ` 이다.

```
주문 Transaction B             관리자 Transaction A
──────────────────────────────────────────────

BEGIN

상품 조회
→ 10,000원

                               가격 변경
                               10,000 → 20,000
                               COMMIT

상품 다시 조회
→ 10,000원

COMMIT

새로운 Transaction
상품 조회
→ 20,000원
```

이렇듯 격리 수준을 통해 여러 트랜잭션이 동시에 실행될 때, 서로의 작업 내용을 어디까지 볼 수 있게 할지 정할 수 있다.

## 동시성 - 격리 수준으로 제어 못하는가?

그러면 왜 동시성을 격리 수준으로 제어 하지 않고, Lock, Redis 등등..여러가지를 붙이는 이유가 뭘까라는 생각이 들었다.

격리 수준이 가장 높은 `SERIALIZABLESER`으로 쓰면 되지만, 만약 4개의 요청이 들어왔다고 생각해보면, 아래와 같이 작업 처리량이 확연히 차이가 나는 걸 알 수 있다.

```

T1 ──────────────>
T2 ──────────────>
T3 ──────────────>
T4 ──────────────>


T1 ──────>
          T2 ──────>
                    T3 ──────>
                              T4 ──────>
```

응답 시간이 길어지고 DB connection도 더 오래 점유하게 되고 결국 connection pool까지 영향을 줄 수 있다.

### AtomicInteger

동시성 테스트를 위해서 테스트 코드를 작성하는 중에, 람다 안에서는 람다 바깥의 지역변수를 람다 안에 쓸 수 없다는 것을 알게되었다.

이를 살펴보니, 자바 람다 캡쳐 규칙이라는 것이 존재했다. 람다 바깥의 지역 변수를 사용하려면, 그 변수는 `final` 이거나 effectively final 이여야 한다는 것이다.

final은 일단, 알다 싶이 값이 변하지 않는 변수여야 한다는 것이고, 그렇다면 effectively final은 뭘까? 아래와 같이 일반 변수로 10을 저장했다고 쳤을 때, `count`는 한 번도 재할당이 되지 않는 변수이다.

소스 코드를 컴파일할 때 컴파일러가 분석해서 판단한다. 별도의 키워드나 런타임 구분값이 있는 것은 아니다.

```java
int count = 10;

System.out.println(count);
System.out.println(count);
```

하지만, 람다 안에서 변수 변경이 필요하다면, 다른 문법을 사용해야한다.

`AtomicInteger`은 여러 스레드가 안전하게 공유하면서 숫자를 변경할 수 있게 만든 객체 카운터다.

```java
count
  │
  ▼
┌──────────────────┐
│ AtomicInteger    │
│ value = 0        │
└──────────────────┘
```

이렇게 접근할 수 있기 때문에, `count.incrementAndGet();` 을 통해서 +1을 한다고 해도 AtomicInteger이 가지고 있는 숫자만 변경된다.

```java

count
  │
  ▼
┌──────────────────┐
│ AtomicInteger    │
│ value = 1        │
└──────────────────┘
```
